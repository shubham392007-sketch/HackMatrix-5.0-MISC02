## MISSION

Extend the existing Skill Passport Domain 1 — Evidence Intelligence & Work Ingestion — to support connecting one GitHub repository during initial setup and adding additional repositories later.

The existing application already has:

- Supabase authentication.
- GitHub Personal Access Token (PAT) connection.
- GitHub repository selection.
- Repository cards.
- Repository language statistics.
- A refresh action.
- Evidence Workspace.
- Connected Sources.
- Upload Work & Docs.
- Evidence Library.
- Ingestion Runs.
- Data & Permissions.
- The existing document extraction and candidate skill analysis pipeline.
- PostgreSQL persistence, Celery/Redis and ChromaDB, according to the existing architecture.

**Integrate this functionality into the existing implementation. Do not build a new GitHub connector, a separate evidence pipeline, another database or a second skill-extraction engine.**

The intended behavior is:

1. During first-time setup, the user connects GitHub and selects exactly one repository for the initial import.
2. That repository is processed through the existing Domain 1 ingestion pipeline.
3. After completing setup, the user can open Connected Sources and see the repositories their current GitHub credentials are authorized to access.
4. The user can explicitly select additional repositories.
5. Each selected repository is imported, extracted, analysed and indexed using the existing processing infrastructure.
6. Repository language statistics and actual README content are available as source context.
7. The evidence and candidate competency results appear in the existing Evidence Workspace.
8. The user can refresh or stop using a repository without unnecessarily disconnecting the entire GitHub account.

There must be no hardcoded repository list, sample language percentages, fabricated README content or fake `ANALYZED` status.

# PHASE 4 — FETCH ACTUAL REPOSITORY LANGUAGE STATISTICS

For every selected repository, call GitHub's official repository-language endpoint:

`GET /repos/{owner}/{repo}/languages`

Use the existing authenticated backend API client.

Do not create a separate PAT flow for language analysis.

## 4.1 Persist real API values

The endpoint returns language names and byte counts.

For every successful result, persist:

- GitHub repository ID.
- Existing Skill Passport repository record ID.
- Authenticated owner ID.
- Language name.
- Actual byte count.
- Calculated percentage.
- Snapshot ID or version.
- Retrieval timestamp.
- Associated sync-run ID.
- Status.
- Safe error details if applicable.

Reuse existing tables and models when compatible. Create a reviewed additive migration only if required.

## 4.2 Correct percentages

Calculate:

`language_percentage = language_bytes / total_reported_language_bytes * 100`

where the total is the sum of all returned language byte counts for that repository.

Use full precision for calculations and round only for display.

Do not hardcode language percentages or language-color mappings as data.

A color can help identify a language visually, but the language name, byte count and percentage must come from actual retrieved data.

## 4.3 Empty and unavailable results

Handle these cases distinctly:

- Valid non-empty language response.
- Empty language mapping.
- Zero total bytes.
- Repository inaccessible.
- Permission error.
- API rate limit.
- Network failure.
- Missing or invalid repository record.

An empty language mapping can be a valid result, while an API failure is not.

Do not turn a failed request into an empty language list without recording the actual failure.

Do not assign a default language to a repository with no reported language data.

## 4.4 Aggregate language analysis

When the user has multiple selected repositories, support an optional aggregate language view.

Calculate aggregate percentages by summing each language's byte counts across all selected repositories before dividing by the combined total.

Do not average per-repository percentages.

Exclude repositories that the user has not selected for evidence ingestion.

Show whether the view represents:

- One repository.
- The selected-repository aggregate.

Do not interpret a repository's language percentage as the user's personal proficiency.

**Acceptance gate:** Language cards and aggregate views use real persisted byte counts and correctly calculated percentages.

1. Request the README through the official API.
2. Handle the repository's actual default branch.
3. Decode the returned content according to the API response format.
4. Validate the response and content encoding.
5. Preserve the README path and Git blob SHA when available.
6. Preserve the GitHub HTML/source URL.
7. Compute or record a content hash.
8. Record the retrieval timestamp.
9. Store the actual README content in the existing private evidence/storage architecture where that is consistent with the current model.
10. Make the content available to the existing evidence-extraction pipeline.

Do not fetch arbitrary raw files directly using a URL constructed from an untrusted model output.

Resolve source paths and links through the correct authorized repository context.

## 5.2 Preserve useful README structure

Extract meaningful README sections, including where present:

- Project title and summary.
- Problem being solved.
- Goals and features.
- Technologies and frameworks.
- Architecture.
- Setup and installation.
- Implementation details.
- Usage examples.
- API descriptions.
- Testing and evaluation.
- Results or screenshots described by the README.
- Limitations.
- Contribution notes.
- Deployment details.
- Relevant project documentation links.

Preserve Markdown headings and section relationships.

Retain useful code blocks where appropriate and within configured size limits.

Normalize formatting where necessary but do not discard technical context simply to produce a short summary.

Remove duplicated boilerplate when safe, but preserve source text and its provenance.

## 5.3 No README available

Some repositories do not contain a README, or the token may lack the permission required to retrieve its contents.

Handle these separately.

If the repository legitimately has no README:

- Record that the README is unavailable.
- Continue with other permitted source data.
- Do not fabricate a README summary.

If access failed because of an actual permission error:

- Record the permission failure.
- Explain what permission or connection update is required.
- Do not treat the README as empty or successfully extracted.

If the README is too large or uses a format the extractor does not support:

- Report the actual condition.
- Apply documented size/format limits.
- Offer an appropriate recovery path.

## 5.4 README provenance

Preserve:

- Repository ID.
- README path.
- README Blob SHA/version.
- Original GitHub URL.
- Extracted section/headings.
- Exact text chunks.
- Content hash.
- Extraction method/version.
- Retrieved timestamp.
- Processing state.

Candidate skills extracted from a README must be traceable to the actual README section that supports them.

**Acceptance gate:** Every selected repository's README is retrieved and processed when available and accessible. Missing READMEs and permission failures are represented honestly.
